# Task 1: Define the Problem

Users need a private task tracker. An unauthenticated visitor must be able to sign up or log in, but cannot access a user's tasks. Authenticated users can create, read, update, and delete only their own tasks. The backend must provide a paginated list for future frontend integration.

## Acceptance criteria

1. A new username is unique, passwords are bcrypt-hashed, and successful signup creates a session.
2. Correct credentials log a user in. Refreshing the supplied React client preserves the session until logout or expiration.
3. Invalid credentials return HTTP 401. Duplicate usernames return HTTP 409. Invalid input returns HTTP 400.
4. Every task operation is protected by a signed session, and the current user's ID comes only from that session.
5. Users do not see, edit, or delete tasks owned by another user. An unauthorized request returns 401; an other-user task ID returns 404.
6. List requests take validated positive `page` and `per_page` parameters and never exceed 100 results per page.
7. Database migrations and an idempotent seed script are available; pytest covers auth and CRUD.
8. Documentation explains installation, database migration, server startup, tests, and every endpoint.

# Task 2: Determine the Design

## Authentication choice

Use **Flask sessions** rather than JWT. The provided session-based React client already expects these route names and payloads, and its `package.json` forwards API requests to Flask port 5555. Authentication credentials are checked against bcrypt hashes. Flask's default session data is signed and stored in an HTTP-only browser cookie; it is not a server-side session store. The session holds `user_id` only, never the password or hash.

## Entity relationships

```text
+------------------------------+      one-to-many     +---------------------------------+
| users                        | 1  -------------- * | tasks                           |
+------------------------------+                     +---------------------------------+
| id: Integer PK               |                     | id: Integer PK                  |
| username: String(50), UNIQUE |                     | title: String(120)              |
| password_hash: String(128)   |                     | description: String(2000)       |
+------------------------------+                     | is_completed: Boolean           |
                                                     | created_at: DateTime            |
                                                     | user_id: Integer FK -> users.id |
                                                     +---------------------------------+
```

## Modules and responsibilities

| File | Responsibility |
| --- | --- |
| `config.py` | Configures database, session cookie, secret key and limits |
| `app/__init__.py` | Constructs the application and registers routes |
| `app/extensions.py` | Centralizes initialized Flask extensions |
| `app/models.py` | Users, tasks, foreign key relationship, bcrypt password helpers |
| `app/routes/auth.py` | Signup, login, check_session, logout and auth decorator |
| `app/routes/tasks.py` | Validates and implements owner-only CRUD and pagination |
| `seed.py` | Creates sample users and tasks without duplicating existing ones |
| `tests/` | Independent in-memory test database for automated tests |

## Endpoints and error policy

See `README.md` for complete endpoint, payload and status documentation. `400` means malformed input; `401` means unauthenticated / bad login; `404` means the task is nonexistent *or not owned by the requester*; `409` means username collision. Deletion returns `204` and no response body.

## Out-of-scope production security upgrades

Before commercial deployment, require HTTPS and secure cookies, implement CSRF tokens for cookie-authenticated writes, add login rate-limiting, monitoring, production database, and strong required environment secrets. This lab demonstrates the auth and ownership fundamentals; it is not a complete production security program.

# Task 3: Develop the Code

See `app/`, `config.py`, `Pipfile`, `seed.py` and the database migration generated by `flask db migrate`. Follow the commands in the README and commit the generated migration folder.

# Task 4: Test, Debug, and Refine

Run `pipenv run pytest -v`. Verify the 31 tests covering input validation, password hashing, session persistence, 401/404/409 status codes, CRUD, pagination, and cross-user access controls. Use curl with a cookie jar and optionally the supplied session frontend for manual verification. If a test fails, fix the implementation, rerun all tests and commit a descriptive message.

# Task 5: Document and Maintain

README lists setup, database migration, seed, run, API contract and testing instructions. Maintain small commits and use at least one reviewed and merged feature PR, preferably three (authentication, tasks, and tests/docs). Commit `migrations/`, `Pipfile`, `Pipfile.lock`, code and test files; never commit local databases, development cookies or secrets.
